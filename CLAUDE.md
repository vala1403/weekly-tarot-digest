# CLAUDE.md

Context for future sessions on decisions behind the current pipeline and
`data/theme-log.json` schema (v2). These aren't derivable from reading the
code alone, so they're recorded here rather than left to be rediscovered.

## Weekly workflow

- Transcripts land manually in `/mnt/c/tarot/<week-of>/` as `{sign}-{n}.txt`
  (n = 1..5), first non-empty line is the source YouTube URL, rest is a raw
  transcript copy-paste. `parse_manual_transcripts.py --week-of YYYY-MM-DD`
  parses these into `transcripts/<video_id>.txt`. It only parses and
  reports; it never tags or aggregates.
- `aggregate_digest.py` **requires** `--week-of` and validates that it falls
  on a Monday. It never infers the week from the run date, since digests are
  routinely produced before the week in question starts.

## theme-log.json schema (v2) decisions

`data/theme-log.json` is a flat log of one entry per sign per week
(`entries: [{week_of, sign, theme, ...}, ...]`), extended from a
theme-only v1 shape to capture the full weekly observation as groundwork
for a future trend view. Full field descriptions live in the file's own
`notes` object; the decisions below are the ones worth knowing before
touching that data.

- **`agreement` is a coverage count, not directional consensus.** It
  reflects how many of the 5 readers the aggregating model judged to have
  touched on a theme similar in meaning to the category's summary. Two
  readers predicting opposite outcomes (e.g. one says reunion, one says
  ending) can both count toward `agreement` if they addressed the same
  topic. That kind of conflict is captured separately in `divergence`, not
  by lowering `agreement`.
- **Per-category `tone`** (a love-specific tone, finance-specific tone,
  etc.) **was never generated by the pipeline** and is intentionally
  omitted from the schema, not backfilled as `null`. Only two tone-like
  fields exist: `reader_tone` (per-reading, free-form vocabulary, from
  `tag_transcripts.py`'s `overall_tone`) and `theme` (per-sign aggregate,
  fixed `THEME_VOCABULARY`). Don't confuse the two or invent a
  category-level tone that was never computed.
- **`channel_name`** was also never captured anywhere in the pipeline
  (only `video_id`, `url`, and paraphrased content exist per reader) and is
  omitted from the reader schema for the same reason.
- **Theme movement in 2026-07-20 through 2026-08-10 is an artifact of the
  `no-repeat-4wk` exclusion rule**, not observed volatility. During that
  window, `aggregate_tone()` excluded a sign's last 4 weeks of themes from
  the vocabulary, so back-to-back repeats were structurally impossible.
  Every one of those 48 backfilled entries has `repeat_streak: 1` for
  exactly that reason. Each entry's `theme_rule` field marks which regime
  produced it (`"no-repeat-4wk"` vs `"repeats-allowed"`) so this isn't
  misread as a genuine trend later.
- **From 2026-08-17, repeats are allowed** (`REPEATS_ALLOWED_FROM =
  "2026-08-17"` in `aggregate_digest.py`). `aggregate_tone()` opens the
  full `THEME_VOCABULARY` and shows the sign's history to the model as
  context only ("not a restriction... do not avoid a theme just because it
  appears in this history"), not an exclusion list. From this date,
  `repeat_streak` becomes meaningful: it increments when the new theme
  matches the immediately preceding week's, resets to 1 otherwise. Whenever
  `repeat_streak >= 2`, the digest's `overall_tone_summary` states this
  plainly and factually (e.g. `"Second week running."`), appended before
  the digest JSON is written, so it flows through to the Spanish
  translation and the HTML page automatically.
- **`capricorn` / `2026-07-27` reader `ID5u08xuJac` has `distinctive_point:
  null`** because `channel_theme` was genuinely blank in that week's
  original digest JSON, not because the backfill script failed to find it.
  This is a listed, human-reviewed gap (`KNOWN_GAPS` in
  `backfill_theme_log.py`), not a silent null.

## Provenance

`backfill_theme_log.py` is a one-time migration script: it rebuilt v2
entries for the four pre-existing weeks from the digest JSONs as they
existed in specific git commits (each week's digest file gets overwritten
weekly, so history only survives in past commits). It refuses to re-run
once `data/theme-log.json` is already `schema_version: 2` — going forward,
`aggregate_digest.py` owns appends directly.
